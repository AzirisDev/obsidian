Cтандартное поведение containerlab: при первом запуске лабы он создаёт management-сеть `clab` и по умолчанию даёт ей две подсети, IPv4 `172.20.20.0/24` и IPv6 `3fff:172:20:20::/64`. Твой вывод в точности это и показывает: 

```
ip -6 addr show scope global  
12: br-158fcf93ead2: <NO-CARRIER,BROADCAST,MULTICAST,UP> mtu 1500 state DOWN  
inet6 3fff:172:20:20::1/64 scope global nodad  
valid_lft forever preferred_lft forever
```

Подсеть `3fff::/20` вообще зарезервирована под документацию и примеры, в интернете её нет, но формально она «глобальная».

Проблема возникает на стыке двух нормальных вещей. Вот что происходит, когда ты пишешь `ping google.com`:
1. Ping спрашивает систему: «какой адрес у google.com?»
2. DNS честно отвечает двумя адресами: IPv4 (A-запись) и IPv6 (AAAA-запись).
3. Система (`glibc`) решает, какой адрес поставить первым. Правило простое: если на хосте есть глобальный IPv6-адрес, значит, IPv6 работает, и он идёт первым.
4. Система видит `3fff:172:20:20::1` на бридже `containerlab` и делает вывод «у меня есть IPv6».
5. Ping пытается отправить пакет на IPv6-адрес Google, но IPv6-маршрута в интернет нет (твой провайдер или роутер IPv6 не раздаёт). Пакеты уходят в никуда.

Ping не умеет откатываться на IPv4, поэтому просто падает. Браузеры и `curl` умеют (механизм Happy Eyeballs: пробуют оба протокола и берут тот, что ответил), поэтому в обычной жизни ты этого не замечал. А вот часть инструментов будет сначала ждать таймаута по IPv6 и только потом пробовать IPv4. Отсюда загадочные тормоза.

Иначе говоря, система делает неверный вывод «IPv6 есть» по адресу, который к интернету отношения не имеет.

### Что с этим делать

Рекомендую вариант с `gai.conf`:
```bash
echo 'precedence ::ffff:0:0/96  100' | sudo tee -a /etc/gai.conf
ping -c 3 google.com
```

Это одна строка, которая говорит: «при выборе адреса ставь IPv4 выше IPv6». Containerlab продолжает работать как раньше, IPv6 внутри лаб тоже. Если когда-нибудь провайдер даст настоящий IPv6, строку можно убрать.

Альтернатива — удалять сеть `clab`, когда лабы не запущены (`docker network rm clab`). Containerlab создаст её заново при следующем `deploy`, но тогда проблема будет возвращаться каждый раз, это неудобно.
